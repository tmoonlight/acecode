# 自动模式（试验）

权限模式 `auto-review`。本来要弹确认的工具调用,先交给一个模型判断:它放行就直接执行,
它拦下就把理由回给主模型,不弹窗。这个模式不依赖系统沙盒,也不需要管理员权限。

机制参照 Claude Code 的 auto 模式(openspec `add-auto-review-mode`)。提示词和规则表是
ACECode 自己写的,按本地开发场景裁剪过。

## 和「自动模式」的区别

两个模式免确认的范围完全一样:只读工具、写边界内的文件编辑、已知安全命令、沙盒可用时的
未知命令。区别只在剩下那些「要确认」的调用:

| | 自动模式(`auto`) | 自动模式（试验）(`auto-review`) |
|---|---|---|
| 要确认的调用 | 弹确认 | 交给裁决模型 |
| 沙盒关着时的未知命令 | 每条都弹 | 裁决放行就执行 |
| 需要确认的 MCP 工具 | 弹确认 | 交给裁决模型 |
| 跑 goal 时 | 一律放行 | 裁决放行才执行 |

沙盒的开关与行为不受影响,见 [sandbox.md](sandbox.md)。

## 一次调用怎么走

1. 规则与工具自检先跑。直接放行或直接拒绝的,照旧。
2. 需要确认时,用户配置的确认类 hook 先跑。它拒绝就拒绝,它放行就放行,都不问裁决。
3. 下面「只能由用户确认」的几类,直接弹确认。
4. 其余的交给裁决模型。

## 只能由用户确认

这几类不交给裁决模型:

- 命中 exec 规则里 `decision="prompt"` 的命令。
- 命中配置里 Deny 规则的文件写入。
- 写入危险路径。
- 进入、退出计划模式。

没有人能确认时(headless、无人值守的 goal、没有确认通道),这几类直接拒绝。

forbidden 规则、内置保护规则、写边界照旧直接拒绝。无人值守时申请沙盒外执行或额外权限,
照旧是 Forbidden。

## 裁决的三种结果

| 结果 | 有人在场 | 无人可问 |
|---|---|---|
| 放行 | 执行 | 执行 |
| 拦下 | 拒绝,理由回给主模型 | 同左 |
| 没有结果 | 弹确认 | 拒绝,提示可稍后重试 |

- **放行**等同点了一次「允许」。执行边界和用户批准时一样,不留下会话记忆,不写规则文件。
  同一条命令再来一次,仍然要过裁决。
- **拦下**之后主模型会收到理由,通常会换一种做法,或在回合结束时向你说明要做什么。
- **没有结果**指请求失败、超时,或模型没按格式回答。这不算拦下,不计数。

### 连续被拦

连续 3 次或累计 20 次被拦之后:

- 有人在场:下一次被拦的调用改为弹确认,确认框里带着裁决的理由。你作答后重新计数。
- 无人可问:锁定。之后需要裁决的调用直接拒绝,不再调用裁决模型;正在跑的 goal 转为
  blocked。你发来下一条消息时解除。

切换权限模式会清零计数。

## 裁决模型看到什么

只有两类内容:

- 你亲手发的消息,以及你对提问的回答。
- 主模型发起的工具调用(名字和参数)。被你拒绝过、被自动模式拦过的调用带有标记。

工具输出、主模型自己说的话都不给它看。所以网页或文件里的文字没法对裁决模型下指令,
主模型也没法用自己的解释说服它。

记录有体积上限。太长时先丢最早的工具调用,你的消息最后才丢。

IM 群聊代答会话里,群成员的话会标成「群成员的消息」,不能当作机主的许可。

## 裁决模型怎么判

默认放行,只有命中规则才拦。规则分两张表:

- **无条件拦**:把密钥或私有数据送到项目自己的远端之外;改动 ACECode 自身的权限规则与
  配置,或用看不懂的编码隐藏命令的真实作用。
- **你点名才放**:不可恢复的删除、丢弃未提交的改动、强推、向外发布、改动生产或共享系统、
  执行从网络下载的代码、削弱安全设置、打印或落盘凭据、系统级改动、代你向他人发消息、
  花钱的操作、授予权限、启动关闭了审批的其它 agent。

「点名」指你的原话里说了那个危险动作本身。「把部署搞好」不等于同意回滚数据库。

裁决分两步。第一步只看操作的后果,宁可错拦;判拦之后才有第二步,结合例外和你的原话复核。
多数调用在第一步就放行,只花一次请求。

## 选择裁决模型

设置 > 工具 >「自动模式（试验）」,下拉里选一个已保存的模型。第一项「跟随当前模型」表示
用会话当前的模型裁决,这是默认值。

配置项是 `config.json` 的 `auto_review.model_name`。接口见
[daemon-api.md](daemon-api.md) 的 Auto (experimental) reviewer settings 一节。

配置的模型被删掉后,自动改用会话当前的模型。

建议单独配一个裁决模型:

- 用同一个模型时,等于让它审自己发起的操作。
- 主对话和裁决共用一个模型,会一起消耗限流额度。

## 成本

每次裁决多一到两次模型请求,提示词约 2000 token,加上对话记录。免确认的调用不产生请求。

裁决请求失败时有人在场就退回弹确认,不会卡住回合。

## 各入口

- **Web / 桌面**:输入框下方的权限菜单,设置 > 常规 的默认权限模式。
- **TUI**:Shift+Tab 循环(默认 → 自动 → 自动（试验）→ YOLO → 计划),或 `/mode auto-review`。
- **IM 通道**:`/mode auto-review`。
- **Headless**:`acecode -p --permission-mode auto-review "…"`。需要确认的调用由裁决决定,
  不再一律拒绝。

三个入口的裁决模型都从同一份配置里取。daemon 与 headless 经会话注册表接线,TUI 在自己的
会话装配处接线。

## 审计

安全中心的审计记录里,裁决的决定来源显示为「模型裁决」,带阶段、裁决模型名和理由。

## 给主模型的提示

打开这个模式时,请求里追加一段说明,告诉主模型被拦之后该怎么做。关闭后追加一条「不再
生效」。静态 system prompt 不变,没进过这个模式的会话请求不受影响。

## 重跑验收

改了规则表或裁决流程后,用真实 daemon 加假模型服务重跑,不访问外网:

- `python -I tests/scripts/auto_review_acceptance_test.py --binary <acecode 可执行文件>`:
  放行、拦下、没有结果、切出模式、跟随当前模型、裁决中打断、审计,以及 headless 下的放行与拒绝。
- 在 `web/` 下 `pnpm build` 之后,设 `ACE_DAEMON_BINARY=<acecode 可执行文件>` 运行
  `node scripts/test-auto-review-mode.mjs`:确认框里的理由、「正在进行安全检查」、设置卡片。
  需要 playwright,用法见脚本开头。

免确认的安全命令(如 `echo`)直接放行,不经过裁决。想观察裁决,要用需要确认的命令,
并且关掉沙盒或让命令申请沙盒外执行。

## 已知限制

- 裁决模型可能判错。放行只等于「允许一次」,硬性规则都在它之前生效,但它不是隔离边界。
- 弱模型可能不按格式回答,表现为频繁退回弹确认。
- 规则表是内置的,暂时不能自定义。
- 项目指令文件不会送给裁决模型。
- 子代理的派发提示不经过裁决。
- provider 接口不能限制输出长度,带推理的模型在第一步也会先思考,较慢。每步有时限
  (20 秒、45 秒),超时按没有结果处理。
