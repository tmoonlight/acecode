## Context

动机见 proposal.md。下面只列决定做法的现状与约束（源码位置为 2026-10-01 的 master）。

**打开会话的现状**

- 侧栏点开未激活会话时，前端同时发出恢复请求和 `GET messages?since=0`。恢复完成后，`useSessionTranscript` 的加载 effect 依赖 `[api, isLive, sid]`，`isLive` 翻转会再发一次 `since=0`（`web/src/lib/sessionTranscript.js:2094`）。
- 恢复（`SessionRegistry::resume`）解析整个 JSONL，再做三轮 O(N) 的工具结果替换、文件检查点加载（O(N)+O(S²)），以及 `restore_file_tool_state_from_messages`。最后这一步对历史上每次 `file_edit`/`apply_patch` 都读一遍当前文件，且不去重（`src/adapters/tool/file_state_restore.cpp:150`）。模型上下文最终只用最新压缩检查点之后的部分。
- `GET messages?since=0` 对已激活会话调用 `SessionManager::load_active_messages()`，在会话锁 `mu_` 内从磁盘重读并解析整个文件（`src/domain/session/session_manager.cpp:926`）。
- 加载器对每行解析两遍（`session_storage.cpp:105` 一遍，`deserialize_message` 又一遍）。下发前每条消息先序列化成字符串再解析回来，再算一次 sha1 作为 id（`message_payload.cpp:33`）。
- `list_active()` 持有注册表锁 `mu_`，逐个调用各会话 `SessionManager` 的取值函数，这些函数都要拿会话锁（`session_registry.cpp:2245`）。于是一个会话的整文件读取会经由注册表锁，拖住所有需要查会话的请求。
- 每轮结束后，自愈校对再拉一次 `since=0`（`ChatView.jsx:646`）。只读外部会话每 1.5 秒拉一次 `since=0`（`ChatView.jsx:641`）。

**侧栏的现状**

- 首屏要等置顶会话、无工作区置顶、置顶排序三个请求都返回后才渲染（`Sidebar.jsx:2531-2566`）。
- 每 5 秒刷新一次：
  - `/api/sessions` 无分页，返回 daemon 自身工作区和无工作区的全部会话，侧栏只留无工作区那部分；
  - 置顶排序为清理失效置顶，读取每个已注册工作区的全部元数据（`server_helpers.cpp:1865`）；
  - 状态订阅每轮对每个工作区都重发，客户端和服务端都不去重（`connection.js:106`、`routes_ws.cpp:82`），每次回一份全量快照。
- "展开显示"第一次就拉全量列表（`Sidebar.jsx:2385`）。
- daemon 启动即预热全局会话目录，扫描全部项目目录，并每 5 秒重列一次（`global_session_catalog.cpp:583`）。

**约束**

- JSONL 是唯一的会话真相，只追加写入。重试、回退等改写操作用"写临时文件再替换"整体重写（`SessionStorage::write_messages`）。
- 多个进程可能写同一个项目目录：TUI、每个工作区一个 daemon、headless、子代理，靠写入租约协调。
- 消息 id 的规则：用户消息是持久化的 UUID；其它消息是内容哈希，可能重复，不能当游标。
- 事件 `since` 是内存里的序号，每次恢复或重启都从头开始。
- 搜索结果用 `message_ordinal` 定位，服务端按 JSONL 全部记录计数（`session_user_message_search.cpp` 的 rebuild 与 `SessionManager::on_message`）；前端给行标的序号却是过滤后数组的下标（`sessionTranscript.js:883`）。从源码看，两者在有文件检查点的会话里会错位，尚未运行验证。
- 压缩检查点有 v1（无窗口字段）和 v2（含 `replacement_history` 与窗口字段）两种。7 月以后的检查点有 2 万 token 的保留上限，体积小。
- Windows 上每次打开文件都要过一遍杀毒软件；冷缓存下逐个打开上千个小文件要数秒。

## Goals / Non-Goals

**Goals：**

- 打开任意大小的会话，首屏耗时只取决于尾部一页，以及最新压缩点之后那一段。
- daemon 在任何整文件读取期间都不持有会话锁或注册表锁。
- 侧栏的首屏、刷新、展开都只读取要显示的那部分会话。
- 旧的全量接口继续可用；每个阶段可以单独发布、单独回滚。
- 用仓库内的隔离基准量化每个阶段的前后变化。

**Non-Goals：**

- 不迁移存储，不改 JSONL 记录格式，不加 SQLite 索引（属于后续阶段，见文末）。
- 不改事件 `since` 的语义。
- 不改 TUI 的恢复显示行为；TUI 只受益于共享的解析和恢复优化。
- 导出、分叉、`@session` 引用这类用户显式发起的全历史操作，仍然按需整读。

## Decisions

### D1 存储不动，只改访问方式

实测的开销来自重复读取、整读和持锁，与存储格式无关。

业界情况：

- Codex 保留 JSONL 作为真相，旁边建可重建的 SQLite 索引，历史按页从尾部读；
- Goose、opencode 迁到 SQLite 之后，长会话照样整段加载；
- Claude Code 至今用 JSONL，而且去掉了原来的 JSON 索引。

备选方案对比：

- 整体迁入 SQLite：仍然需要分页；要处理多进程写入、存量迁移；数据目录可能放在网络盘上，SQLite 在网络盘上锁不可靠。被否。
- 现在就加 SQLite 索引：在阶段 0 的数据出来之前，看不出收益是否值得这份一致性成本。推迟。

### D2 位置标识：记录起始字节位置加记录指纹

分页游标与搜索定位，统一使用"某条记录在文件中的起始字节位置"。游标是一个不透明字符串，编码 `{offset, fingerprint, file_identity}`，指纹是该行内容的哈希，文件身份取 OS 句柄的卷/文件编号或 device/inode 的哈希。

- 服务端收到游标，先校验两件事：`offset` 处是行首（位置为 0 或前一个字节是换行）、该行指纹一致；任一不符就返回 409 `HISTORY_CURSOR_STALE`。
- 只追加不会改动已有行，所以旧游标一直有效；整体重写会改变文件身份，即使锚点行正文相同也必须失效。
- 这种游标不用维护任何代次计数，对其它进程的写入也成立。

备选方案：

- 在 meta 里放一个"重写代次"计数：所有重写路径（包括其它进程、旧版本）都必须正确递增，脆弱。
- 用行号：要得到尾部记录的行号，得从文件头数换行，冷缓存下等于整读一遍文件。

### D3 尾部倒读

新增一个倒读器：从文件末尾按 64 KiB 的块向前读，按换行切行，参考 Codex 的 `reverse_jsonl_scanner`。

- 末尾没有换行的半行，沿用现有恢复语义处理。
- 隐藏记录的过滤：先在原始字节里查找 `compact_checkpoint`、`file_checkpoint` 这类子串做预筛，命中后再完整解析确认，避免消息正文里恰好出现这些词时被误判。其余行照常解析。
- `before` 页从游标处继续向前读；`after` 请求从游标处向后读到当前文件末尾。
- 返回前先记下读取开始时的文件大小，只读到这个位置为止。同时进行的追加不会让一页里出现半条记录。

### D4 页的起点对齐到回合开头

规格允许一页多于 `limit` 条。服务端在凑够 N 条之后，继续向前延伸到最近的一条可见用户消息，让前端不必处理从半轮开始的页；延伸上限是 4N 条，超过就停在 N 条，并在响应里标记 `turn_truncated: true`。

默认 `limit` 由前端传入，初值 200，用隔离基准调优。

### D5 打开会话只加载一次

**阶段 1（保留旧接口语义）**：历史 effect 只依赖会话与连接身份，`isLive` 翻转不取消或重发磁盘读取。实测 `subscribe(since=0)` 原本只订阅未来事件，不能补齐恢复时的第 1 条审计消息，因此增加显式 `replay_from_start` 标志；旧 since=0 与 since>0 语义保持。磁盘会话变成实时后用该标志补齐事件，已有订阅也先退订等待在途投递，再建立回放订阅。首次 REST 请求期间缓冲 WS 事件，加载落地后在同一次 store 提交中重放，避免旧快照吞掉新审计或流式事件；副作用不重复派发。

**阶段 2**：首次加载改为 `since=0&limit=200` 的尾部页。

备选方案：先恢复、再只加载一次（搜索面板的打开路径就是这么做的）。代价是在恢复完成之前看不到任何历史，体验退步。被否。

### D6 缩小锁的范围

- `load_active_messages()` 改为：在锁内只取出文件路径和当前文件大小，离开锁之后再读取、解析到该大小为止。读完再看一眼文件，发现被整体重写（文件身份或开头指纹变了）就重试一次。
- Windows 实测补充：锁内打开原生只读句柄并记录身份和大小，不读内容；锁外读取并复核。会话 JSONL 原子重写启用 `ReplaceFileW`，允许读快照继续访问旧文件，避免 `MoveFileEx` 对已打开目标返回拒绝访问。
- `list_active()` 改为：在注册表锁内只复制各会话条目的 `shared_ptr` 列表，离开锁之后再逐个取字段。
- 侧栏要用的标题、摘要、轮数、用量这些显示字段，归入每个会话一份单独加锁的小快照。这样读取它们不会和消息落盘争用同一把锁。

### D7 每行只解析一次，响应直接构造

- 新增从已解析的 JSON 对象构造 `ChatMessage` 的反序列化入口，加载器只解析一遍。
- 响应 JSON 直接由 `ChatMessage` 构造，不经过字符串往返。
- 消息 id 规则不变（用户消息用 UUID，其它消息用内容哈希）。
- 同一份 103MB 文件，Python 全量解析 0.3 秒，daemon 约 1.5 秒，优化空间足够。

### D8 恢复：倒扫到最近的压缩点，全历史依赖改为用到再加载

- 用 D3 的倒读器找到最新的有效压缩检查点（v1、v2 都接受，只要含 `replacement_history`），向前解析它之后的记录。
- 解码失败就继续向前找上一个有效检查点；一个都没有，就退回整读。
- 用倒扫结果和整读结果，比对重建出的模型上下文，作为单测的不变量。
- 只用后缀部分来源的状态：模型消息、工具结果替换状态、文件工具状态。文件工具状态按路径去重，每个文件最多读一次。压缩时本来就清空了读取观察（`compaction_window.cpp:134`），所以压缩点之前的读取状态本就不该恢复。
- 改为第一次用到时再加载：
  - 文件检查点存储：第一次回退、查看差异统计或判断能否恢复时，才单独扫一遍 `file_checkpoint` 记录，同样用子串预筛；
  - 检查点备份目录的清扫，随之推迟。
- 压缩控制器的 `initialize_window()` 改为倒扫取最新检查点，不再调用整读。
- 去掉 `ConversationHistory::restore` 在恢复路径上每条消息一行的误报警告：恢复时 worker 尚未开始运行，这时的修改是合法的。

### D9 搜索跳转与时间轴改用字节位置

- 搜索索引表新增"该用户消息起始字节位置"一列。追加时位置就是追加前的文件大小，重建时随解析一起记录。表结构变化通过重建派生索引完成，索引本来就可以丢弃重建。
- 搜索结果带回这个位置，前端跳转时请求"从目标位置到当前已加载部分"的连续区间，一次补齐（D2 的游标）。
- 只有序号、没有位置的旧链接：服务端按换行计数把序号换算成位置。这一步只在用户显式跳转时发生。
- 分页之后前端不再自己数下标，D9 顺带消除了"服务端按全部记录计数、前端按过滤后下标计数"的口径差异。实现前先写一个回归测试复现这个错位：多轮会话里跳到第 N 条用户消息。

### D10 自愈与只读轮询

- 自愈校对改为请求尾部页，`limit` 取"本地最近一轮的条数加一个余量"。如果这页里没有作为锚点的用户消息，再补一页。
- 只读外部会话的轮询带上一次响应的 `after` 游标。返回空就什么都不做；返回 409 就重新加载尾部页。

### D11 侧栏

- `GET /api/sessions` 新增 `scope=no-workspace`，只枚举无工作区会话。侧栏改用它，其它调用方保持原样。
- 置顶会话与置顶排序：清理失效置顶，改为逐个检查置顶 id 对应的元数据文件是否存在，成本 O(置顶数)；不再调用 `session_ids_for_workspace`。
- 状态订阅：
  - 客户端只在某个工作区尚未出现在 `statusWorkspaces` 中、或连接刚重建时才发送订阅；
  - 服务端对同一连接上已订阅的工作区，重复订阅时不再发送快照。
- 展开：取消 `full: true`，按"当前行数加 5，再加置顶数"请求有界页。接口已经支持 `limit` 与 `has_more`，不需要新增分页参数。
- 首屏：会话行在有界页返回后立即渲染，置顶标记与排序到达后再合并进来。
- 子代理查询 `?parent=` 改为按父会话所在的项目目录做有界查询。
- 合并导航触发的刷新：打开一个会话时，`revealTarget`、`activeWorkspaceHash` 的变化合并成一次刷新。

### D12 预热推迟

`GlobalSessionCatalogIndex::start()` 改为等待两个条件中先到的一个：首个工作区会话列表请求完成，或启动满 10 秒。期间如果收到会话搜索请求，立即开始。

### D13 诊断

- 服务端：在读取、列表、恢复的路径上用一个作用域计时器记录耗时和读取量，按规格要求的级别写入日志。
- 前端：每次打开会话后，把耗时上报到新增的 `POST /api/diagnostics/session-open`。浏览器模式与 Desktop 走同一条路径，失败直接丢弃。
- 数据诊断：新增 `GET /api/diagnostics/sessions` 与 `acecode diagnose sessions`，两者共用同一份统计逻辑。
  - 只统计已注册的工作区。
  - 每个工作区只逐行分析最大的 5 个会话文件，按记录类型用子串预筛分类计数，不保留任何内容。

### D14 隔离基准纳入仓库

- 新增 `scripts/bench/session_loading/`：
  - 生成器：生成带工具输出、净差异、检查点的合成记录，大小和条数可控，不依赖本机的真实会话；
  - 测量脚本：用假的 `USERPROFILE` 起一个隔离 daemon，测列表、恢复、历史请求的耗时。
- 浏览器端测量沿用 `performance.getEntriesByType('resource')` 和长任务观察。
- 每个阶段完成后，把前后数字记进本 change 的 `verification/` 目录。

## Risks / Trade-offs

- [不持锁读取时恰好遇到整体重写] → 只读到开始时记下的文件大小，读完复核文件身份与开头指纹，不一致就重试一次；重试仍失败，返回 409 让前端重新加载。
- [子串预筛误判] → 命中后都会完整解析确认；只会多解析，不会漏掉可见消息。
- [前端拿到的是半轮开始的页] → D4 对齐回合开头；超过上限时用 `turn_truncated` 标记，前端照常投影。
- [跳到很早的消息时一次补齐的区间很大] → 只在用户显式跳转时发生，结果与现在整读相当，可以接受。
- [预热推迟后，启动后立即打开搜索会稍慢] → 收到搜索请求时立即开始预热，进度照常返回。
- [失效置顶改为惰性清理] → 显示结果不变，只是清理时机后移。
- [搜索索引加列需要重建] → 索引本来就可以丢弃重建，按项目在后台进行，重建期间退回现有路径。
- [`after` 轮询漏掉"改写但大小不变"的情况] → 指纹校验能发现，返回 409。

## Migration Plan

- 没有数据迁移。接口只做新增；前端不传 `limit` 时就是原来的行为，回滚前端即可回到旧路径。
- 按阶段 0 → 1 → 2 依次合入，每个阶段单独验收：
  - 阶段 0 先上线，收集用户侧数据；
  - 阶段 1 不改接口，可以随任意版本发布；
  - 阶段 2 前端与 daemon 同包发布（Web 资源嵌在同一个二进制里）。
- `docs/daemon-api.md` 与 `CLAUDE.md` 的相关段落随阶段 2 同步更新。

## 后续阶段与进入条件（不在本 change 内）

- **阶段 3：可重建的 SQLite 索引（`add-session-index-cache`）。**
  - 进入条件：阶段 1、2 合入后，阶段 0 的数据仍显示冷启动列表 p95 超过 500 毫秒，或单个工作区超过 2000 个会话很常见，或"按序号跳转"需要的换行计数成为瓶颈。
  - 做法：每个项目一份元数据加字节位置的派生库，沿用 `user_message_search.sqlite3` 的模式（短连接、按签名判断新鲜度、坏了就重建、不可用时退回文件扫描）。库里只放能从文件重新算出来的字段。
- **阶段 4：JSONL 瘦身（`slim-session-records`）。**
  - 进入条件：诊断显示用户数据里，每轮净差异或文件检查点占比超过 20%，或者超过 1MB 的单条记录很常见。
  - 做法：每轮净差异的单条记录设上限（如 64KB），超出部分照大工具输出的方式放到 `<会话id>/` 下的单独文件；文件检查点改为增量（Claude Code 有先例）。压缩检查点不动。

## Open Questions

- 默认页大小按条数还是按字节：先按 200 条，用基准调优，不影响规格。
- 预热推迟的具体时长：默认 10 秒，可调。
- 打开耗时上报是否顺带上报侧栏首屏耗时：可以后续扩展字段。
