## Context

`ChatView` 持有预览页签和文件 `edit` 状态，现有关闭动作已经使用 `Modal` 与 `saveEditableFileDraftBatch`。文件切换直接更新页签，`App` 更新导航历史，`Sidebar` 还存在直接激活 Desktop 工作区并重定向的入口，单独监听切换后的 sessionId 无法实现“取消不切换”。

## Goals / Non-Goals

**Goals:** 在动作执行前统一决定，保存成功或丢弃后只执行一次原动作，失败与取消不离开当前编辑现场。

**Non-Goals:** 本变更仅覆盖未保存确认，不能代表原始会话级缓存需求已完成；完整归属改造由后续 `isolate-session-workbench-state` 补齐。不修改聊天输入草稿，不接管浏览器或操作系统自身的窗口关闭/刷新行为。

## Decisions

1. 使用一个可注入保存/丢弃回调的确认控制器，管理单个待处理请求、保存中状态与错误。干净路径同步放行，存在修改时返回等待用户决定的 Promise。关闭、页签切换、会话切换共用控制器和弹窗。
2. 预览状态通过唯一提交函数同步更新 ref 和 React state，确认读取最新文件版本，避免保存完成后第二层导航再次看到旧 dirty 标志。保存复用现有 read_id 校验通路，失败保留修改，不新增文件写入接口。
3. 页签切换检查当前活动文件；会话/工作区导航检查当前可见页签中的全部脏文件。每次请求捕获原归属和相关页签键，保存/丢弃只更新这些文件。再次点击当前文件不提示。
4. `ChatView` 向 `App` 注册离开检查，`App` 导航提交与 Desktop resume/重定向前调用，`Sidebar` 在本地选择状态和原生工作区激活前也调用。相同导航身份的元数据更新保持放行。
5. 自动浏览器页签前置也经过预览选择入口；原生页面选中与面板展开必须等确认。已有确认期间拒绝额外请求，卸载时取消等待，保存失败可重试。

## Risks / Trade-offs

- [多层导航检查重复弹窗] → 确认成功前同步提交干净/丢弃状态，后续检查直接放行。
- [保存期间异步回调串入其他会话] → 保存操作捕获原文件归属，未确认不能导航，卸载后不执行旧请求。
- [部分文件保存成功后另一文件失败] → 保留全部页签，已成功文件更新基线，失败文件保留修改，再次保存仅处理仍未保存的文件。
- [原生自动选页绕过确认] → 将 select 延后到确认后的回调，覆盖浏览器自动前置和手动新建入口。

## Migration Plan

无需持久化迁移。按确认控制器、预览入口、会话/工作区入口、交互验证顺序实施，整体回退本变更即可恢复旧行为。
