## 背景

当前 Web/Desktop 共用的升级入口通过 `/api/update/start` 创建后台任务，前端通用请求层默认在 30 秒后中止请求，升级核心又把 `upgrade.timeout_ms` 同时用于清单和安装包下载。更新任务仅能轮询，后端没有取消信号，前端关闭对话框也只会隐藏任务。顶部入口始终使用完整主色背景，无法表达进行中的百分比。

升级跨越网络下载、校验、解压和安装替换。下载前中止是安全的；一旦进入安装替换，强行中断可能留下不完整安装，因此取消能力必须有明确边界。

## 目标 / 非目标

**目标：**

- 升级过程不再因为固定 30 秒总时限被误判为失败。
- 用户可以取消尚未进入安装替换的图形界面升级任务。
- 取消状态可轮询、可恢复展示，且不会触发重启。
- 顶部按钮保持现有尺寸和轮廓，以填充比例和正确的双色文字表达进度。

**非目标：**

- 不允许在已经开始替换安装文件后强制终止。
- 不改变命令行升级的交互方式，也不新增外部依赖。
- 不改变更新清单格式、包校验和回滚机制。

## 技术决策

### 1. 升级网络请求使用无限总时限

升级清单与安装包请求不再传入固定总时限；连接断开、HTTP 错误、写盘错误仍按原逻辑失败。前端启动升级的请求显式使用无超时模式，避免通用 30 秒默认值中止它。

保留现有配置字段的兼容读取，避免旧配置失效；该字段不再限制自升级下载，仍可供当前共用的反馈上传逻辑使用。

### 2. 使用协作式取消，不杀死升级线程

升级核心接收一个线程安全的取消检查回调。下载写入回调在收到取消请求后返回失败以中止传输；校验、解压及安装前的阶段边界也检查取消状态。取消使用专用退出码与结果标志，避免把用户操作显示成普通故障。

不采用强制终止线程，因为它可能打断文件写入、资源清理或安装事务。

### 3. 安装开始后关闭取消窗口

任务状态增加 `cancel_requested` 与派生的 `can_cancel`。`POST /api/update/jobs/:id/cancel` 只对当前活动任务生效：安全阶段返回 202 并设置取消标志；进入 `installing` 后返回 409。升级核心在发布 `installing` 之前执行最后一次取消检查，从而保证前后端边界一致。

取消成功后任务进入终态 `cancelled`，清理未使用的下载与暂存目录，`restart_required` 保持为 `false`。重复取消已经取消的同一任务按幂等成功处理。

### 4. 顶部进度按钮使用同位双色裁切层

按钮外壳继续使用现有高度、最小宽度、水平内边距与圆角。进行中状态渲染三个完全重合的层：未填充底层显示主色文字；主色背景按百分比从左向右裁切；白色文字副本使用同一裁切范围。这样每个字形落在主色背景上的部分为白色，落在透明背景上的部分为主色，并且按钮在任意百分比下都保持可读。

进度值沿用现有全生命周期映射并限制在 0 到 100；按钮提供包含百分比的无障碍标签。

### 5. 2026-10-07 更新入口迁移到侧边栏底部

用户截图指定的底栏位置覆盖前述顶部位置约定。App 将现有更新状态和打开弹框回调传给 Sidebar，按钮位于底部设置菜单与问题反馈按钮之间，紧邻反馈按钮左侧并靠右排列。TopBar 移除更新属性与渲染；原有 24px 高度改用按钮自身的 `h-6`，避免依赖顶部栏局部 CSS 变量和顶部偏移。

保留新版可用时才显示、启动时禁用、更新中进度填充、已更新标签和点击打开更新弹框的行为。侧栏折叠时隐藏该入口，重新展开后展示当前状态；设置菜单检查更新、后端任务、下载、取消与重启流程不变。

## 风险 / 权衡

- [服务端长时间无响应且用户尚未取得任务编号] → 启动 API 仍先做可用性确认；前端不再误报超时，实际下载开始后可随时取消。后续如需取消清单探测，可再把预检完全移入任务线程。
- [取消与安装开始同时发生竞态] → 后端在同一任务锁下判断阶段并写入取消标志，升级线程在进入安装前执行最后检查；进入安装后统一拒绝取消。
- [底层 HTTP 库把主动中止报告为网络错误] → 下载结果单独记录 `cancelled`，升级核心优先映射为用户取消。
- [短暂阶段进度跳变] → 继续使用现有单调进度映射，顶部和对话框读取同一结果。

## 迁移方案

本次无需数据迁移。旧配置中的 `upgrade.timeout_ms` 继续可读取，不影响启动；新前端会使用新增取消接口与状态字段。回滚时旧前端会忽略新增 JSON 字段，旧后端则不会收到新前端版本。
