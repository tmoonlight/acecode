## Context

当前 master 存在用户已完成但未提交的界面和系统提示改动；四个远端 PR 与这些改动部分重叠。先记录原始状态和哈希，审核增量，再在当前分支合并，避免覆盖既有工作。正式版本以 v0.9.22 为基线；v0.9.23 打包检查发现 Linux 编译问题，修正后完整发布 v0.9.24。

## Goals / Non-Goals

**Goals:**
- 四个 PR 的最终代码经过执行路径审核和针对性回归验证。
- 每次正式版均具备 Windows、Linux、Linux old、macOS 的完整下载集合。
- 不以缺包成功状态发布；GitHub 和更新镜像的哈希、版本与来源一致。

**Non-Goals:**
- 不将旧工作树中的无关实验纳入本次发布。
- 不重设计已有用户界面，不将 macOS PKG 当作自动更新包。

## Decisions

1. 使用独立、可离线测试的产物验证入口，按发布版本匹配必需文件；在生成校验和和调用 GitHub Release 之前失败退出。保留已有的 macOS updater 精确选择规则。
2. 正式标签构建在开始原生打包前校验应用和安装器签名凭据。PKG 签名和公证失败应使发布失败，不降级为没有 PKG 的发布。
3. 审核拖放的 DOM 目标与输入框接收者、桌面实例的显示身份与运行资源所有权、成功与失败请求的计量边界。仅修复由源代码和回归测试支持的问题，并在任务清单记录结果。
4. 本地已完成改动先单独提交，随后合入各 PR 并提交修复；推送前检查差异与测试，推送后验证 PR 状态、CI 和所有发布产物。
5. 嵌入前端的 CMake 配置同时追踪文件名集合和文件内容变化，避免开发启动器重建同名 Vite 产物后继续嵌入旧界面。使用最小真实 CMake/Ninja 工程验证修改文件后自动刷新嵌入字节。
6. Linux WebKitGTK 引入的 X11 `Status`、`Success` 宏必须在平台头文件边界清理，避免改写业务状态枚举。常规 Linux CI 同时编译 Desktop，将此类平台编译问题提前到发布前暴露。v0.9.23 标签打包由此失败，保持标签不可变，修复后以 v0.9.24 完整发布。

## Risks / Trade-offs

- 强制 PKG 会使签名凭据缺失的正式发布提前失败，这是完整发布的必要约束。
- macOS 原生和多架构 ABI 只能在对应 runner 上完整验证；本地执行离线测试，GitHub CI 承担平台测试。
- 跨 PR 与本地改动可能冲突；逐个合并，保留双方行为并补充交叉路径测试。

## Migration Plan

完成审核与本地验证后推送 master，等待分支检查，通过正式标签触发打包。校验完整资产清单后同步更新镜像，核验公网文件与 GitHub 哈希，确认 master 与远端同步。
