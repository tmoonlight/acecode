## Context

见 proposal.md。现场请求轨迹显示两次工具均成功，第二次调用/结果随后被历史修复移除。`recover_provider_history` 当前跨整个历史维护 `seen_call_ids`，不区分同一数组重复与下一条 assistant 的新调用。该函数已被恢复、压缩、请求准备及 OpenAI / Anthropic 提供者共同使用。

## Goals / Non-Goals

**Goals:** 在共同入口修复实时和已保存历史的 ID 冲突，保持已存在的缺失结果、系统上下文穿插、非法条目清理约定。

**Non-Goals:** 不修改已存会话、不改变工具执行 ID 或界面事件、不新增重试或尾部虚构用户消息、不改变提供者认证及模型配置。

## Decisions

1. 单条 assistant 使用局部 ID 集合去重。全局集合只用于发现跨消息复用，发现后保留调用并改名；继续全局丢弃会丢失已执行结果，仅在新响应入口改名无法修复已存历史。
2. 预扫描输入保留所有原始调用及结果 ID，按顺序分配 `call_ace_recovered_<序号>` 并跳过占用值。只为冲突 ID 改名；无随机数或时间依赖，重复投影幂等。直接追加原 ID 后缀可能超过提供者长度限制，也容易与原始 ID 碰撞。
3. 待处理调用以原始 ID 映射到投影 ID，按当前 assistant 的调用顺序补全缺失结果。收到真实结果后只改副本的 tool_call_id，保留附件、metadata、内容及顺序；映射在下一条非 system/tool 消息前清理。
4. 沿用 `duplicate_tool_calls` 统计发现的重复 ID（同数组被丢弃或跨消息被重映射），不扩展 API 字段。回归分别验证处理效果。
5. 测试用脱敏的截图/视觉分析顺序复现现场，覆盖三个连续复用、用户续接、并行结果乱序、系统消息穿插、中断补全、同批重复、候选碰撞、幂等和输入不变，并验证两个提供者最终协议。图片反馈既有测试中直接丢弃跨消息同 ID 的预期改为逐轮保留且图片不串用，并补充后续调用缺失结果不复用旧图的约束。

## Risks / Trade-offs

- 同一数组内同 ID 无法可靠区分不同调用 → 保持首个有效调用及首个结果的既有规则。
- 新 ID 若占用后续原始 ID 将破坏唯一性 → 预留整个输入的调用/结果 ID，并以碰撞回归覆盖。
- 请求会经过多层历史修复 → 对修复输出再次处理必须无变化。
- 预扫描增加一遍线性遍历及 ID 集合 → 复杂度仍为线性，不复制工具结果正文。

## Migration Plan

构建更新后的程序后，下一次请求或会话恢复自动生成修复投影，不需要数据迁移。回退代码不改变磁盘原始会话。当前运行实例是否切换至新构建与源码验证分别记录。
