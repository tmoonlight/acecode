# 设计

## 发布范围

复用受保护 master 的集成与版本 PR。近期 worktree 按固定窗口与完成依据盘点；已经包含的提交及内容等价补丁不重复应用；源码和最终包分别验证。

## 本机测试进程结果

GTest 重复运行仅把最后一轮结果写入 XML，进程退出码反映所有轮次。运行器逐进程结合这两个信号：退出码 0 正常；退出码 1 且该进程 XML 记录断言失败时，继续现有失败与基线对照；其它非零退出必须阻断。超时使用的负数退出码保持在 JSON 中，避免同组成功进程通过 max 运算将其覆盖为 0。

解析失败、缺失 XML 与已有基线失败维持原有判断。生产 MCP 连接与配置读写代码保持本次输入基线；首次失败与压力重复中的启动超时如实保留，最终全量结果另行验证。

## 通道测试回调生命周期

Linux CTest 在三个微信用例的断言全部通过后报告 double free。测试先声明传输对象、后声明记录器，导致记录器先析构，而传输对象析构中的 stop 仍会发送最终状态或排空消息。直接提取现有 Recorder 与生产 TransportCallbacks 类型构造停机回调最小复现，Linux ASan 报告 heap-use-after-free；仅调整声明顺序后通过。

统一将微信、QQ、Telegram、飞书、Discord 测试中的 Recorder 放在传输对象之前，保证正常结束和 ASSERT 提前返回时，传输对象都先停机。钉钉和 LINE 已遵循此顺序。生产 PlatformRuntime 的回调经 LifetimeRef 进入宿主，析构体先调用 stop，断开时先停止传输对象，保持现有生产实现。
