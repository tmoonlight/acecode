# src/pa — PA 内网模型服务的客制化故障适配层

这个目录只放一类代码:**上游服务端的行为与公开协议不一致,导致 ACECode 的
通用判定失效**,需要一层按报文特征识别、并归一化回通用故障类别的适配。

## 为什么单独建目录

这些兼容代码有三个共同点,混进通用路径会越来越难维护:

1. **只对特定环境成立** —— 判定依据是某个服务端的具体报文,不是协议约定。
2. **会过期** —— 上游修好之后这里就该删,所以必须能一眼找全。
3. **必须可解释** —— 每一条都要写清楚观测到的原始报文长什么样,否则半年后
   没人敢动。

因此通用代码里只留一个**兜底调用点**,判定逻辑全部收在这里。

## 边界(不要越过)

- **不硬编码服务地址、模型名、账号、业务名词。** 只按报文特征判定 —— 同一个
  真实模型在 `saved_models` 里常有多个别名,按名字匹配必然漏。
- **不放业务逻辑。** 这里只做「把非标准故障翻译成 ACECode 已有的故障类别」。
- **纯逻辑优先。** 判定函数不碰 IO、不依赖全局状态,直接单测(`tests/pa/`)。
- **失败方向要安全。** 判不出来就返回 `None` 走原有路径,绝不猜。

## 当前收录的故障

### 1. 上下文超限错误认不出(`pa_quirks.{hpp,cpp}`)

**观测报文**(HTTP 400):

```json
{"object":"error","message":"请求上下文过大","type":"BadRequestError","code":400}
```

**通用路径为什么认不出**:`compact.cpp::is_context_overflow_error` 的判定是
英文 needle 集(`context_length_exceeded` / `prompt is too long` / …)加 OpenAI
标准错误码(`context_length_exceeded` / `input_too_long` / …)。上面这条报文
文案是中文、`type` 是非标准的 `BadRequestError`,两套都不命中。

**后果**:ACECode 现成的三级恢复链(修剪历史重试 → 精简请求档重试 → 报错)
整个不启动,400 直接抛到界面,用户只能手动 `/compact` 或重开会话。

**适配**:`pa::is_context_overflow()` 补一组中文特征串,由
`is_context_overflow_error` 兜底调用。**故意不限制状态码** —— 该网关的状态码
本身就是不可信的那一环,而中文特征串足够专指,不会误伤其它错误。

### 3. 瞬时故障被塞进 4xx 返回(`pa_quirks.{hpp,cpp}`)

**观测报文**:

```json
{"code":400,"message":"LLMRequestError: 模型服务异常，请稍候重试，如持续出现，请联系技术支持","type":"BadRequestError"}
{"code":502,"message":"LLMRequestError: 网络波动或模型处理超时，请稍候重试"}
```

**通用路径为什么不够**:`retry_policy.cpp` 对 4xx 一律不重试(注释写着「客户端
错误即使提到 overload 也是终止性的」)。这条规则对守规矩的上游是对的,但这套
网关把瞬时故障也编成 400,一次本该自动恢复的抽风就成了永久失败。

**适配**:`pa::is_transient_upstream()` 由 `provider_http_error_is_retryable`
在 4xx 规则之前兜底。收录标准比上下文超限**更严** —— 必须是报文自己写着「这是
暂时的、可以再试」,否则真正的客户端错误会被无限重试。两条刻意不收:

- `LLMRequestError` 这个网关统一前缀同时罩着瞬时故障和参数错误,按它重试等于
  对所有 4xx 都重试。
- 单独的「重试」二字 —— 额度用完的报文写的是「请切换模型后重试」,那是要人换
  模型,不是让程序再发一次。

分类顺序上**上下文超限优先**:超限报文也可能带「请稍候重试」的客套话,但盲目
重试同一个超大请求只会再撞一次墙,必须先走压缩。

### 2. 声明的上下文窗口不准(`pa_context_budget.{hpp,cpp}`)

**现象**:同一个模型的实际可用上下文会变,常常远小于 `saved_models` 里声明的
`context_window`。实测出现过上下文占用显示 55% 就被服务端拒绝的情况。

**通用路径为什么不够**:自动压缩的触发阈值是「声明窗口 × 90%」。声明值虚高
时这个阈值永远够不到,每一轮都要先撞一次墙、触发一次恢复重试才能继续 ——
即使故障 1 修好了,每次撞墙仍然要多花一个完整请求的时间和 token。

**适配**:`pa::ContextBudgetLearner` 按 (provider, model) 记录**观测到的最小
被拒请求规模**,把该模型的压缩用窗口收敛到那条线之下。撞过墙才生效,没撞过
完全不干预。进程级、不落盘 —— 服务端限制会变,把一次偶发低水位永久钉死
比不学更糟。

三条踩过的坑,改这块之前先看:

- **一条观测要么可信要么丢弃,没有中间态。** 第一版把
  `PA_CONTEXT_BUDGET_MIN_CREDIBLE_REJECTION_TOKENS` 当成「收敛的下界」用
  (`max(rejected * 85%, floor)`),结果一次 **2726 token** 的拒绝把声明
  128000 的窗口砍到了 8192 —— 只剩 6%,之后每个回合都在压缩。2726 tokens 撑
  不爆任何能用的模型,这种拒绝必然另有原因,正确处理是**整条丢弃**。而且必须
  在 `note_rejected` 入口丢:观测单调取最小值,噪声一旦进表就永久钉死
  `lowest_rejected`,真实观测再也压不进来。
- **身份不明(model 为空)时既不记录也不查表。** 否则所有匿名观测落进同一个
  桶,A 模型的一次拒绝会拖累毫不相干的 B 模型。
- **观测表是进程级单例,单元测试之间共享。** 上面那个 floor bug 的暴露方式就是
  跨测试污染:`AgentLoopCompactEvents`(内含构造上下文溢出的用例)跑完后,
  `AgentLoopToolResultStorage` 的一个无关用例开始失败 —— 它断言的 tool 消息被
  提前触发的自动压缩摘要掉了。现在靠可信下限挡住了测试里那些小规模的构造用
  例,但如果将来有测试构造**真实规模**(≥ 8192 tokens)的溢出,污染会重新出现。
  届时的正解是把 learner 改成依赖注入(AgentLoop 持指针,默认指向全局单例),
  而不是继续调阈值。
